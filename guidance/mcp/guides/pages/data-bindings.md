clio MCP data-bindings guide

Core contract
- Resolve exact binding tool shape through `get-tool-contract` before the first invocation in a workflow.
- Use `get-guidance` with `name` set to `data-bindings` for canonical workflow knowledge about lookup seeding and binding artifact selection.
- Do not copy request schemas, aliases, or response shapes from consumer-repo docs.

Progressive discovery
- Identify whether the task is inline lookup seeding, standalone DB-first binding work, or local binding artifact work.
- Load only the contracts needed for that path:
  - `sync-schemas` for inline lookup seed rows
  - `create-data-binding-db`, `upsert-data-binding-row-db`, and `remove-data-binding-row-db` for remote DB-first binding work
  - `create-data-binding`, `add-data-binding-row`, and `remove-data-binding-row` for local artifact workflows
- MUST: the target package has to be EDITABLE on the environment: its `Maintainer` equals the `Maintainer` system setting AND its `SysPackage.InstallType` is 0. A package created in the app qualifies; a package installed from an archive (`push-pkg`, `push-workspace`, a marketplace install) has `InstallType` 1, and a package whose `Maintainer` differs (for example a package built with `new-pkg`, which writes the `Maintainer` from the clio environment settings, empty when that is not set) fails the first condition. Every DB-first binding write into such a package fails with `SaveSchema failed: Item "<binding>" was either created by a third-party publisher or installed from the file archive`. Do not retry the binding unchanged. Prefer a package owned on this environment: create it in the app, or choose one that already passes both conditions. Use `unlock-package` (needs cliogate) only for a package that is yours, for example one you pushed from your own repository, and always with an explicit `package-names`: it rewrites the package `Maintainer` to this environment's, and without `package-names` it unlocks every package of that maintainer. Never unlock a marketplace or another publisher's package to bind into it — the vendor's next update replaces the package and the binding disappears with it. After an unlock, the refusal persists for a login session that already saw the package as locked, while a new login succeeds (observed on Creatio 10.2 on 2026-11-11: the long-lived clio MCP session kept refusing even after an application restart, a fresh clio CLI process succeeded). An MCP-only agent gets a new login by restarting the clio MCP server; when it cannot, hand the retry to the user.
- Before creating or removing a binding, inspect what the package already ships: the binding tools have no list mode, so read `SysPackageSchemaData` with `execute-esq` (filter `SysPackage.Name`; columns `Name`, `SysSchema.Name`). `binding-name` defaults to the schema name, so pass it explicitly to target an existing binding (often a suffixed folder) instead of creating a parallel one.

Preferred workflows
- Canonical lookup seeding flow: `get-tool-contract` -> `sync-schemas` -> refresh/read-back.
- Canonical standalone DB-first binding flow: `get-tool-contract` -> `create-data-binding-db` -> optional `upsert-data-binding-row-db` -> refresh/read-back.
- Lookup value translations (multilingual app):
  - Availability: use `localizations` only when `get-tool-contract` for `sync-schemas` / `create-data-binding-db` lists it on `seed-rows[*]` / `rows[*]`. A clio whose contract does not list it ignores the key silently: enter the translations in Creatio (lookup record, language switch) instead, and tell the user that translations entered that way are written to this site only, not into the binding already saved, so they do not ship with the package unless the binding is saved again.
  - MUST: when the app serves users in more than one language, ASK the user for the lookup values in each language before seeding — a value written only in your profile culture shows empty or untranslated to everyone else.
  - Shape: put them in the row's optional `localizations` next to `values`, keyed by culture, then column, with text values: `{"values":{"Name":"New"},"localizations":{"uk-UA":{"Name":"Нове","Description":"Новий ремонт"}}}`. It works in `sync-schemas` `seed-rows[*]` and in `create-data-binding-db` `rows[*]` (the same command runs underneath). `upsert-data-binding-row-db` takes no `localizations`.
  - Refusals: only active cultures (Languages section) and columns the schema marks localizable (`Name`, `Description` of a `BaseLookup` descendant, or a text column you made localizable) are accepted; a value longer than its column is refused; a value in your profile culture MUST also be in `values` with the same text (put it in `values`, or leave that culture out of `localizations`) — one missing from `values` or different is refused; any of these refuses the WHOLE call before any write, and the error names each refused record, culture and column.
  - Verification and reporting: the call writes the translations before saving the binding, so they ship with the package, reads every culture back, and fails with "saved, but NOT verified" on a difference. A "written, but not verified" WARNING (the site default culture could not be read) is not a failure: tell the user to check that record in Creatio. The result lists one `Localized row: <Id> (<Name>) [<culture>]: <columns>` line per record and culture — MUST report those, not the request.
  - Existing rows: to translate rows that already exist, read back each row's `Id` first, then call `create-data-binding-db` again with the same rows carrying both `Id` and `Name` plus `localizations`. A row matched by `Name` (in your current profile culture) or by `Id` is not rewritten, so its `Id` and other values stay; a row that matches neither (renamed in the UI, seeded in another culture, sent without `Id`) is INSERTED as a new record, a duplicate lookup value.
  - Records of another package: a record bound in ANOTHER package (a base lookup the app extends) is not moved: it stays there and is also added to the binding you write, so its translations ship with your package; that other package's binding keeps its previous translations until it is saved again.
- `upsert-data-binding-row-db` decides by primary key: it UPDATES a row that already exists in the table (matched by `Id`) and INSERTS only a genuinely new row (which must then carry every required column). The binding must exist first (`create-data-binding-db`, which may be empty).
- Canonical local artifact flow: `get-tool-contract` -> `create-data-binding` -> `add-data-binding-row` or `remove-data-binding-row` -> local artifact verification -> APPLY (below). The local flow ends at a file on disk. `create-data-binding` writes `packages/<Pkg>/Data/<Binding>/{descriptor,data,filter}.json` and touches no environment, so verifying those files proves the artifact is correct and proves NOTHING about the target table.
- Applying a local binding artifact: the artifact is a TRANSFERABLE SOURCE, not an applied row. Exactly two things materialize it. (1) Package installation — `push-pkg` (package data installs BY DEFAULT; `--install-package-data false` suppresses it) or `push-workspace` (installs package data unconditionally — it exposes no such option), which is what carries the binding to the NEXT environment. (2) The DB-first tools — `create-data-binding-db` then `upsert-data-binding-row-db` — which write the live row AND register it in the package, i.e. they are a strict superset of writing the row with `odata-create`. `pkg-to-db` does NOT apply data: it registers package DEFINITIONS from the file system into the configuration database, and installs no binding rows into any business table. Do not read its success as the row having landed; read the row back (`read-data-binding-db`, or `odata-read` on the target schema).
- Applying in file system mode (FSM): FSM is where this goes wrong most often, because the workspace flow that ends at a local artifact and the FSM flow that ends at `pkg-to-db` look like the same flow and are not. In FSM the shipped workspace `AGENTS.md` forbids `push-workspace` and `compile-creatio` (the "rebuilds from the stale DB copy and overwrites your good filesystem build" rationale the template gives is `compile-creatio`'s — do not reason from it that `push-workspace` is safe on a fresh DB copy), and `pkg-to-db` does not apply data — so neither of the two obvious moves applies the row. Apply the identical values with `create-data-binding-db` / `upsert-data-binding-row-db` against the linked environment, then read back. Keep the local `Data/` artifact as the transfer source for the next environment.
- A DB-first binding write in FSM reaches the DATABASE ONLY: `sync-schemas` (`create-lookup` registration, `seed-rows` / `seed-data`), `create-data-binding-db`, `upsert-data-binding-row-db` and `remove-data-binding-row-db` all save through the platform's binding SaveSchema, which has no file-system branch, so `Data/<binding>/` in the package folder is neither created nor updated while the call reports success. clio 8.1.0.139 and earlier give no warning; 8.1.0.140 and later warn, naming the folder and `pkg-to-file-system` (evidence: [`PackageDataBindingWriter.cs`](https://github.com/Advance-Technologies-Foundation/clio/blob/38f48025490a34f1d9c58ce089d97150e64cfe93/clio/Command/PackageDataBindingWriter.cs)). Before committing that package folder, bring `Data/<binding>/` onto disk by ONE of these routes:
  - One binding, without an export (EXPERIMENTAL: derived from clio source, not yet run end to end on a Creatio stand; the route to take when an export is not safe, see the next route): (1) `read-data-binding-db` (`package-name`, `binding-name`) gives the binding `uId`, its columns and every bound row with its `Id`. (2) Local `create-data-binding` with the same `package-name`, `schema-name` and `binding-name`, and the FIRST row in `values`: its `Id` and EVERY column the read reported, because the descriptor's columns come from this call's `values` and `localizations`. Pass lookup columns as `{"value":"...","displayValue":"..."}` and translations of localizable columns in `localizations`. (3) Set `UId` in `Data/<binding>/descriptor.json` to the `uId` from step 1: `create-data-binding` generates a NEW `UId` unless a descriptor is already on disk, so without this edit the folder describes a different binding; later calls keep the edited `UId`. (4) `add-data-binding-row` once per remaining row, each with its `Id` (without one it generates a new key, i.e. a new row) and `displayValue` on every non-null lookup column (not resolved from the environment). (5) Check (MUST): `descriptor.json` has the `UId` and the columns that `read-data-binding-db` reports, and `data.json` holds exactly the row `Id`s it reports (same count, same keys); never commit the folder on a mismatch. Evidence: [`DataBindingCommand.cs`](https://github.com/Advance-Technologies-Foundation/clio/blob/38f48025490a34f1d9c58ce089d97150e64cfe93/clio/Command/DataBindingCommand.cs), clio 8.1.0.127 and later. Until a clio release exports one binding itself, this is the only route that leaves the rest of the package folder untouched.
  - Whole package: `pkg-to-file-system` (via `clio-run` over MCP), right after the DB-first write and before further on-disk edits; then check that `read-data-binding-db` reports the `UId` the exported `descriptor.json` carries. MUST: the export deletes on-disk items the database lacks, so commit or preserve on-disk work first and confirm with the user; when other sessions or agents work in the same workspace, follow "Exporting in a shared workspace" in `fsm-mode` first. On-disk edits made between the write and the export, and not yet imported, are overwritten and never reach the next `pkg-to-db`.
- DB-first SaveSchema metadata should be projected from the primary key plus columns referenced by currently bound or requested rows. That projection is also the transfer contract: a column you never passed is absent from `Data/<Schema>_<Suffix>/data.json` and package install supplies NO default for it, so the row arrives on the next environment with that column empty. Pass every column the target schema needs to be usable, not just the ones you happen to be changing, and verify what actually ships with `read-data-binding-db` (`package-name` + `binding-name`) rather than by reading the live row back. It reports the shipped column set, the row count, and every bound row in one read-only call, so `download-application` + extract is only needed when you want the raw archive. One difference to expect: it lists localizable columns inline, while the export moves them into a `Localization` folder — so it can show one more column than `data.json` for the same binding.
- Clio-generated bindings default every non-key column to `IsForceUpdate: false`, so installing corrected row values does NOT overwrite an existing target row, and re-installing an unchanged descriptor applies no data at all. For ordinary seed data, treat the first install as the only automatic chance and repair an already-transferred row manually. A deliberately package-owned configuration record is a controlled exception: an author may set its mutable columns to `IsForceUpdate: true` and advance the binding descriptor's `ModifiedOnUtc` so package upgrades replace those values. Document that ownership because force update overwrites environment-side customization; `custom-mcp-tools` applies this policy to package-owned `McpTool` metadata.
- `sync-schemas` `seed-data` runs the SAME `create-data-binding-db` command underneath, but it cannot pass `binding-name` — the binding always lands under the BARE schema name. That is fine for a lookup you own, and wrong for any schema whose package already ships suffixed bindings: seeding `SysWorkplace` this way adds a third, parallel `SysWorkplace` binding next to the app's `SysWorkplace_MyApps` / `SysWorkplace_Todo` (verified). When the binding name matters, call `create-data-binding-db` / `upsert-data-binding-row-db` directly with an explicit `binding-name`; the column-projection rule above applies identically either way.
- `remove-data-binding-row-db` is NOT a package-only operation: it DELETES THE LIVE RECORD (DataService delete) and then unbinds it. It is a delete tool with a binding side effect, and there is no tool that removes a row from a package while leaving the record in place. It is also flagged destructive but accepts NO `confirm` argument, so nothing holds the call — get the user's agreement yourself first, and never call it to "tidy up a binding" on a row you still want or on a row shared with other apps.
- Unrelated runtime-only columns are not blockers for DB-first flows; explicitly requested unsupported runtime columns are blockers.
- Permission-protected system objects are OUT OF SCOPE for DB-first binding WRITES: rows are applied through the DataService, which enforces object permissions, so a schema such as `SysEntitySchemaOperationRight` is refused even when the authenticated user is Supervisor. Do not retry, do not switch credentials, and do not treat it as an authorization mistake to fix — the failure names the refusal explicitly. One exception: `create-data-binding-db` ADOPTS a row that already exists (matched by `Name`, then by `Id`) without writing it through the DataService, so binding an existing row of such a schema works; inserting a new row, `upsert-data-binding-row-db` and `remove-data-binding-row-db` are still refused. `sys-settings` relies on this to ship a setting (`SysSettings` / `SysSettingsValue`): create the row with the owning tool first, then bind it. For record-level access rights use `set-record-rights` (native RightsService). Object-operation rights are set and bound to a package by `set-object-rights`, not through a DB-first binding: `get-guidance name=object-rights`.

Lookup seeding rules
- Prefer inline seed rows in `sync-schemas` when the lookup is already part of the current schema batch.
- Use a separate binding artifact only when the workflow explicitly needs one.
- Seed rows do not implement defaults.
- Generate fresh GUIDs for explicit rows at execution time.
- Seed-data replay safety is keyed on `Name`: a row is replay-safe only when the target schema has a `Name` column AND the row carries a `Name`; rows without a `Name` (or schemas without a `Name` column) are non-convergent — a stable-`Id`, no-`Name` row PK-conflicts on replay. Re-running a `sync-schemas` batch whose seed rows carry a `Name` skips the already-present rows (no duplicates); do not add explicit `Id`s to no-`Name` rows expecting a re-run to be safe.

Verification discipline
- Read before write when the task depends on current app, page, schema, or binding context.
- Read back after remote mutation.
- Do not treat install logs or planned payloads as proof of installed remote state.
- Verify local artifacts by inspecting generated files or normalized command output.
- Never treat a planned row list as proof of installed state.
- A local artifact verified on disk is NOT a verified row. When the task is "the value must be present in the environment", the read-back MUST hit the environment (`read-data-binding-db`, or `odata-read` on the target schema), never the workspace files.

Anti-patterns
- Do not duplicate live contract tables in skill docs.
- Do not use direct SQL as the canonical MCP path.
- Do not treat lookup seed rows as default implementation.
- Do not treat `pkg-to-db` as an apply step for binding data, and do not report a binding as delivered on the strength of it.
- Do not stop a binding task at local artifact verification when the task was to configure an environment. That leaves a valid, deployable artifact in the workspace while the environment stays unconfigured, and every command involved reports success.
- Do not leave `DisplayValue` semantics implicit for non-null lookup or image-reference row payloads.

FSM descriptor compatibility
- The modern .NET Creatio FSM reader tested in September 2026 rejects `ReferenceSchemaName` in binding column descriptors. This is an observed compatibility boundary, not a claim about every Creatio version. Keep generator-only lookup hints out of `descriptor.json`; retain lookup `Value` and `DisplayValue` in `data.json`.
- Before transferring older local bindings, inspect their column descriptors. Remove only `ReferenceSchemaName` and advance `ModifiedOnUtc`, preserving identity, rows, and localizations. Regeneration with clio 8.1.0.127 or later replaces existing content: supply all intended rows and localizations again.
- `pkg-to-db` imports package definitions, not data rows. Apply the data through package installation or the DB-first binding tools. Inspect item-level synchronization errors: Clio before 8.1.0.127 may report completion when the server returned `success: true` with nonempty `errors`. A completion message alone is insufficient.
- After applying the binding, read back the expected target rows and, for published MCP tools, verify `tools/list` and the intended call. Do not infer installed state from generated files.
