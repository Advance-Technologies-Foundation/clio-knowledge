clio MCP data-bindings-details guide — writing one database binding to disk in file system mode

A details article of the data bindings guide, reached through `data-bindings`, which points here and is read first.
This article is the authoritative owner of what the `from-environment` route of `create-data-binding` writes and the evidence for it, of the steps of the by-hand route that writes one binding to disk without an export, with their evidence, of which clio versions warn after a DB-first write in FSM, of the package-owned configuration record exception to `IsForceUpdate: false`, of what `read-data-binding-db` reports, of binding an existing row of a permission-protected schema, and of FSM descriptor compatibility (which descriptor fields an FSM import rejects, transferring older local bindings, what `pkg-to-db` imports and reports, and the read-back after applying). `data-bindings` owns when each route applies, the order in which they are tried, the whole-environment export and its MUSTs, and the check every route must pass before the folder is committed; read that first.

Warning after a DB-first write in FSM
- After the call reports success, clio 8.1.0.139 and earlier give no warning; 8.1.0.140 and later warn, naming the folder and `pkg-to-file-system`; 8.1.0.158 and later name the `from-environment` route first (evidence: [`PackageDataBindingWriter.cs`](https://github.com/Advance-Technologies-Foundation/clio/blob/333e9fa669e4df5bc0e14c0e2a2e6989d941f7d6/clio/Command/PackageDataBindingWriter.cs)).

One binding, with clio (`from-environment`)
- It writes `Data/<binding>/` as the platform package export does, because it copies what the binding stores: the registration and its columns become `descriptor.json` (the binding `uId`, `ModifiedOnUtc`, install type and every column with its `IsForceUpdate`), the stored data snapshot becomes `data.json`, and every culture's stored snapshot that has rows becomes `Localization/data.<culture>.json`. It replaces only that binding folder (refusing a folder of another schema) and writes nothing when a read fails. Evidence: run on Creatio 10.2.959 (.NET Framework, MSSQL) against all 10 bindings of a section package; every file was JSON-equal to the package export of the same package (descriptor columns compared in name order), with the same file set per binding; and on Creatio 10.3.1154 (PostgreSQL 16), where the platform stores each data and culture snapshot with a leading byte-order mark: the written data and localization files kept it and were byte-identical to the export ([`DataBindingSnapshotReader.cs`](https://github.com/Advance-Technologies-Foundation/clio/blob/333e9fa669e4df5bc0e14c0e2a2e6989d941f7d6/clio/Command/DataBindingSnapshotReader.cs)).

One binding by hand, without an export
- Steps: (1) `read-data-binding-db` (`package-name`, `binding-name`) gives the binding `uId`, its entity schema (`schema:`), its columns and every bound row with its `Id`; it prints a lookup as `<display value> (<id>)`. The translation condition of this route in `data-bindings` exists because `read-data-binding-db` prints localizable columns in ONE culture (your profile culture) and nothing reads the binding's other cultures back; the values you hold are the `localizations` you seeded it with. (2) Local `create-data-binding` with the same `package-name` and `binding-name`, `schema-name` set to the schema step 1 printed, and the FIRST row: its `Id` and EVERY column the read reported, because the descriptor's columns come from this call's `values` and `localizations`, and `add-data-binding-row` refuses a column the descriptor lacks (`Column '<name>' is not part of binding`). Pass localizable columns (for a lookup: `Name` and `Description`) in `localizations`, under the culture `read-data-binding-db` printed them in (your profile culture; `en-US` in the verified run) and under every other culture the binding carries, not in `values`: `values` writes them into `data.json`, while the platform export of a binding saved by `create-data-binding-db` keeps them only in `Localization/data.<culture>.json`. Pass a lookup as `{"value":"<id>","displayValue":"<display value>"}` and an empty lookup as `{"value":null,"displayValue":""}` (a bare `null` writes the display value `"null"`). These shapes are what a binding saved by `create-data-binding-db` stores; the export copies what each binding stored when it was saved, so a binding saved another way can differ (observed on 10.2.959: a binding saved by the section wizard stores an empty lookup with the display value `"null"` and keeps localizable columns inline in `data.json`, with no `Localization` folder). On a clio without `from-environment`, such a binding takes the whole-environment export, under its MUSTs in `data-bindings`. (3) Set `UId` in `Data/<binding>/descriptor.json` to the `uId` from step 1: `create-data-binding` generates a NEW `UId` unless a descriptor is already on disk, so without this edit the folder describes a different binding. Running `create-data-binding` again later keeps the edited `UId` but rewrites `data.json` and `Localization/` with its one row, dropping the others. (4) `add-data-binding-row` once per remaining row, each with its `Id` (without one it generates a new key, i.e. a new row), the same `localizations` and a `displayValue` on every lookup; it does not resolve display values and refuses a lookup without one. The platform export also writes an empty-string file for every other culture; the route writes only the cultures it was given. Evidence: [`DataBindingCommand.cs`](https://github.com/Advance-Technologies-Foundation/clio/blob/38f48025490a34f1d9c58ce089d97150e64cfe93/clio/Command/DataBindingCommand.cs), clio 8.1.0.127 and later; run on Creatio 10.2.959 (.NET Framework, MSSQL) with clio 8.1.0.137 against a three-row lookup binding with text, integer, boolean, lookup, empty-lookup and localizable columns, compared file by file with the package export, then installed with `push-pkg` on a second environment, where `read-data-binding-db` reported the same `uId`, columns and rows.

FSM descriptor compatibility
- The modern .NET Creatio FSM reader tested in September 2026 rejects `ReferenceSchemaName` in binding column descriptors. This is an observed compatibility boundary, not a claim about every Creatio version. Keep generator-only lookup hints out of `descriptor.json`; retain lookup `Value` and `DisplayValue` in `data.json`.
- Before transferring older local bindings, inspect their column descriptors. Remove only `ReferenceSchemaName` and advance `ModifiedOnUtc`, preserving identity, rows, and localizations. Regeneration with clio 8.1.0.127 or later replaces existing content: supply all intended rows and localizations again.
- `pkg-to-db` imports package definitions, not data rows. Apply the data through package installation or the DB-first binding tools. Inspect item-level synchronization errors: Clio before 8.1.0.127 may report completion when the server returned `success: true` with nonempty `errors`. A completion message alone is insufficient.
- After applying the binding, read back the expected target rows and, for published MCP tools, verify `tools/list` and the intended call. Do not infer installed state from generated files.

Package-owned configuration records
- A deliberately package-owned configuration record is a controlled exception to the `IsForceUpdate: false` default that `data-bindings` owns: an author may set its mutable columns to `IsForceUpdate: true` and advance the binding descriptor's `ModifiedOnUtc` so package upgrades replace those values. Document that ownership because force update overwrites environment-side customization; `custom-mcp-tools` applies this policy to package-owned `McpTool` metadata.

What `read-data-binding-db` reports
- It reports the shipped column set, the row count, and every bound row in one read-only call, so `download-application` + extract is only needed when you want the raw archive. One difference to expect: it lists localizable columns inline, while the export moves them into a `Localization` folder — so it can show one more column than `data.json` for the same binding.

Binding an existing row of a permission-protected schema
- `create-data-binding-db` ADOPTS a row that already exists (matched by `Name`, then by `Id`) without writing it through the DataService, so binding an existing row of such a schema works; inserting a new row, `upsert-data-binding-row-db` and `remove-data-binding-row-db` are still refused. `sys-settings` relies on this to ship a setting (`SysSettings` / `SysSettingsValue`): create the row with the owning tool first, then bind it. Every other write to such a schema stays refused, as `data-bindings` says.
