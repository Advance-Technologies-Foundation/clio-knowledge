clio MCP theme background guide

Scope
This guide owns a custom theme's own background: reading, setting, changing and removing it, its Creatio version floor, the panel icon side effect, and the package binding of its image. The theme itself — create, restyle, delete, list, apply, the default theme — is in `get-guidance name=theming`.

Theme background
A theme can carry its own background, an image or a color, which its accounts see instead of the site background (`get-guidance name=branding` → "Background" owns the site background and which one an account sees). Only `create-theme` and `update-theme` write it, and only the no-code flow keeps it: the `theme.json` that `build-theme` writes has no background, so the next `push-workspace` drops one set on a workspace theme — tell the user.
- Read: `list-themes` and `get-theme` return `background` as `{ mode: "Image", imageId }` or `{ mode: "Color", color }`, and leave it out when the theme has none.
- Set: pass at most one of `background-image-id` (upload the file with `upload-image` first) or `background-color` (#RGB, #RRGGBB or #RRGGBBAA; convert another form with `advise-theme-palette operation=triage`) to `create-theme` (brand mode too) or `update-theme`; `remove-background` on `update-theme` clears it. With a background argument `update-theme` needs only the `id` — the omitted `caption`, `css-class-name` and `css-content` keep their values, so never send the CSS for a background change.
- Version: Creatio 10.2.96 or later. On an older one a call with any background argument, `remove-background` included, fails with `version-too-old` and writes nothing. After a failed `create-theme`, tell the user and repeat it without the background argument. After a failed `update-theme` the theme is unchanged: tell the user this Creatio cannot carry a theme background, and never fall back to `create-theme`. Set the site background instead only if the user agrees. A clio whose `create-theme` contract has no `background-color` cannot set one — ask the user to update clio.
- Panel icon: setting a background leaves `UsePanelIconBackground` off for All employees (turned off if it is on), because it can cover the background — an environment-wide change, so tell the user before the write that it will be off for everyone. Pass `keep-icon-background` = true only if the user asks to keep it; if the user declines the turn-off for everyone, write the background with `keep-icon-background` = true and tell them the panel icons can cover it. The result says which: `panel-icon-background` (`off` or `kept`) from `create-theme`, a log line from `update-theme`. A failed turn-off is a warning.
- Package: a failed write changes nothing else; an image uploaded for it stays, unbound. After a successful one an image is bound into the theme's package — for an existing theme the `Pkg/<package>` segment of its `cssFilePath` (check it with `get-target-package`), not a branding run's target package — which `create-theme` returns in `background-image-package` and `update-theme` names in its log; a color travels inside the theme. The theme write does not bind the panel icon state, only a site background does, so unless the theme's package also carries a site background, on another environment the icon background can still cover the theme background — tell the user. A binding problem is a warning — the theme exists, do not create it again; relay the warnings (`create-theme` returns them in `warnings`, `update-theme` in its log). `remove-background`, a `background-color` that replaces an image, and `delete-theme` keep the image binding, so the package still ships the image — tell the user.
