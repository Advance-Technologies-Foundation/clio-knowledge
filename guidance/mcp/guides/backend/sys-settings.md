clio MCP sys-settings guide

Core contract
- Resolve the exact tool shape through `get-tool-contract` before the first invocation in a sys-setting workflow.
- Use `get-guidance` with `name` set to `sys-settings` to recall the rules below; do not copy schemas from consumer-repo docs.
- Sys-settings expose four MCP tools: `list-sys-settings`, `get-sys-setting`, `create-sys-setting`, `update-sys-setting`. All operate on the All-Users default; per-user overrides are out of scope for this surface.
- All tools accept named JSON arguments wrapped under `args`. Do not pass positional CLI-style arguments.
- None of the four are advertised in `tools/list` — they are long-tail tools discoverable through `get-tool-contract` (each carries a `resident: false` flag); their absence from `tools/list` is expected, not a blocker.
- Invoke the read-only tools (`list-sys-settings`, `get-sys-setting`) through the `clio-run` executor: `{"command": "list-sys-settings", "args": { …target args… }}`. Invoke the destructive tools (`create-sys-setting`, `update-sys-setting`) through `clio-run` with the same shape (`clio-run-destructive` is a deprecated alias of it). Do not call any of the four by bare name — strict/HTTP MCP clients cannot dispatch an unadvertised bare name.

Tool call shapes (the `args` payload below goes inside the executor's own `args` field unchanged)
- `list-sys-settings` — `{ "args": { "environment-name": "<env>" } }`
- `get-sys-setting` — `{ "args": { "environment-name": "<env>", "code": "<setting code>" } }`
- `update-sys-setting` — `{ "args": { "environment-name": "<env>", "code": "<setting code>", "value": "<new value>" } }` (optional `value-type-name` fallback when the setting cannot be located on the environment). For `Binary` settings pass `value-file-path` (a local file path) instead of `value`.
- `create-sys-setting` — `{ "args": { "environment-name": "<env>", "code": "<setting code>", "name": "<display name>", "value-type-name": "<type>", "value": "<initial>", "reference-schema-name": "<entity>" } }` (`value` and `reference-schema-name` are optional except where noted below)

Preferred workflows
- Discover then read: `list-sys-settings` → `get-sys-setting` when the code is unknown.
- Read then mutate: `get-sys-setting` → `update-sys-setting` for existing settings.
- Provision: `create-sys-setting`. When `value` is supplied, clio internally invokes `update-sys-setting` so the response already carries the read-back value.
- Provision for a package: `create-sys-setting` (with `value`, or then `update-sys-setting`) → read the two row ids → `create-data-binding-db` for `SysSettings` → `create-data-binding-db` for `SysSettingsValue` → `read-data-binding-db` for both. See "Shipping a setting with a package" below; this guide owns that procedure.

Shipping a setting with a package
- MUST: `create-sys-setting` and `update-sys-setting` change ONLY the environment they run against. The setting is not part of any package. When package code, a page, a process or a business rule reads the setting, ship it with the package that reads it, or the next environment that installs the package has code reading a setting that does not exist. Nothing fails loudly: a backend `SysSettings.GetValue(userConnection, code, defaultValue)` returns its default (for a Lookup, `Guid.Empty`), and a page read returns an empty value.
- A setting ships as TWO bindings in the owning package, named by convention after the code (the same pair the Creatio designer produces):
  - `SysSettings_<Code>` on schema `SysSettings`: the definition. Row columns: `Id`, `Code`, `Name`, `Description`, `ValueTypeName`, `IsCacheable`, `IsPersonal`, `IsSSPAvailable`, and for a `Lookup` setting also `ReferenceSchemaUId` (without it the setting arrives with no lookup target). `Name` and `Description` are localizable: the package export moves them into the binding's `Localization` folder.
  - `SysSettingsValue_<Code>` on schema `SysSettingsValue`: the All employees default value. Row columns: `Id`, `SysSettings` (the definition's `Id`), `SysAdminUnit` = `a29a3ba5-4b0d-de11-9a51-005056c00008` (All employees), `IsDef` (`false`), `Position` (`2147483647`), and the typed value column for the setting's type (plus `TextValue` on clio 8.1.0.149 and earlier, see below).
- The typed value column: `IntegerValue` (Integer), `BooleanValue` (Boolean), `FloatValue` (Float, Money), `DateTimeValue` (Date, Time, DateTime), `GuidValue` (Lookup), `TextValue` (the Text family), `BinaryValue` (Binary). Integer and Lookup bindings were created and read back, and only Integer was also transferred to a second environment; the other types follow the designer-made pair's column set.
- MUST NOT ship a `SecureText` value through a binding: the stored value is encrypted by the source environment, and nothing has verified that it decrypts on another one. Ship the definition only and have the value set on each environment. clio 8.1.0.150 and later refuse such a `SysSettingsValue` row before any write.
- `TextValue`: clio 8.1.0.150 and later always include the `SysSettings` and `TextValue` columns in a `SysSettingsValue` binding themselves, so the row does not need `TextValue`. On clio 8.1.0.149 and earlier you MUST pass `TextValue` in the row, as `""` when the setting is not a text type; without it `create-data-binding-db` fails with `SaveSchema failed: Value "TextValue" was not found.` (observed for Integer and Lookup settings, also reported for Float), even though the row never mentions that column. Passing it on a newer clio is harmless.
- MUST: pass `binding-name` explicitly (`SysSettings_<Code>`, `SysSettingsValue_<Code>`). The default is the bare schema name, so a second setting in the same package would go into the same `SysSettings` binding. `sync-schemas` `seed-data` cannot pass `binding-name` and is therefore the wrong tool here (`data-bindings` owns that rule).
- MUST: set the value on the environment BEFORE you bind it, with `create-sys-setting` `value` or `update-sys-setting`. The All employees `SysSettingsValue` row exists only once a value has been set — a setting created without `value` has no such row, and you MUST NOT invent its `Id`. `create-data-binding-db` binds an existing row as it is in the database (it reports `Skipped existing row` and does not write the values you passed), so the binding ships whatever the environment holds at that moment. `update-sys-setting` is the only write path for the value: `SysSettings` and `SysSettingsValue` are permission-protected, so `upsert-data-binding-row-db` and `remove-data-binding-row-db` are refused on them. Binding works only because `create-data-binding-db` adopts the existing row without writing it (`data-bindings` owns the permission-protected rule, this exception and the existing-row match rule).
- Read the ids instead of inventing them: `execute-esq` on `SysSettingsValue` filtered by `SysSettings.Code` AND `SysAdminUnit` = `a29a3ba5-4b0d-de11-9a51-005056c00008`, with columns `Id`, `SysSettings.Id`, `SysAdminUnit.Id` (without the `SysAdminUnit` filter a setting with personal or role values returns several rows). For a Lookup, also read `SysSettings.ReferenceSchemaUId`.
- Verify what ships with `read-data-binding-db` (clio 8.1.0.99 or later) for each binding. The bound `SysSettings` row `Id` MUST equal the definition `Id` you read: an existing row is matched by `Name` first (case-insensitive, across all settings — `data-bindings` owns the match rule), so a definition whose `Name` equals another setting's binds THAT setting instead, still reporting `Skipped existing row`; give the setting a unique `Name`. The value binding must carry the typed value column with the value you expect — a binding whose value column reads empty ships an empty default.
- A Lookup value ships only the referenced record's id. When the record is not standard data that already exists on every target, ship it too (`data-bindings` owns lookup seeding), or the setting arrives pointing at nothing.
- Changing a setting that already shipped: the value binding holds the row as it was when the binding was saved, so after `update-sys-setting` on the source the package keeps shipping the OLD value until you run `create-data-binding-db` for `SysSettingsValue_<Code>` again and read it back. On targets, the bindings carry `IsForceUpdate: false`, so a package update does NOT overwrite the value on an environment that already has the setting (`data-bindings` owns this rule and the force-update exception).
- MUST: bind into a package that is editable on this environment (`data-bindings` owns the rule and the `third-party publisher or installed from the file archive` refusal). Create `SysSettings_<Code>` first, then read it back with `read-data-binding-db` and check that the bound row `Id` is the definition `Id` (see the `Name`-first match below) before binding the value. The value binding fails with `SaveSchema failed: Data is not bound for connected object "SysSettings" by column "SysSettings"` when the definition binding is missing OR when it bound another setting's row by `Name`; in the second case re-creating `SysSettings_<Code>` changes nothing, so give the setting a unique `Name` instead.
- In file system mode the DB-first binding write does not reach the package folder. Follow the `pkg-to-file-system` rule in `data-bindings` before committing.
- Evidence: the column sets above match the designer-made pair `SysSettings_KnowledgeIndexingBatchSize` / `SysSettingsValue_KnowledgeIndexingBatchSize` in package `CrtAIKnwLibApp`. The procedure, the `TextValue` failure (on clio 8.1.0.149 and earlier), the skipped existing row and the refused upsert and remove were observed through clio MCP on Creatio 10.2 (.NET Framework, MSSQL) on 2026-11-11 for an Integer and a Lookup setting; the `TextValue` failure was also reported for a Float setting. The transfer itself was verified end to end on 2026-11-11: an Integer setting bound into a scratch package on one Creatio 10.2 environment, exported with `pull-pkg`, and installed with `push-pkg` on a second environment that did not have the setting arrived with its All employees value (`get-sys-setting` read it back). The `Name`-first match is clio's `create-data-binding-db` behavior. On clio 8.1.0.150 or later, on 2026-11-13, a Decimal, a Lookup and a Text setting were bound by following this guide with value rows that omitted `TextValue`, and `read-data-binding-db` showed each value row with its own setting, All employees and the expected value.

Supported value-type-name
- Text family: `Text`, `ShortText` (Text 50), `MediumText` (Text 250), `LongText` (Text 500), `MaxSizeText` (Unlimited), `SecureText` (Encrypted string).
- Scalars: `Boolean`, `DateTime`, `Date`, `Time`, `Integer`.
- Numerics: `Money` (canonical), `Float` (canonical). Aliases accepted: `Currency` → `Money`, `Decimal` → `Float`.
- `Lookup`: requires `reference-schema-name`. Pass the entity schema name (for example `Contact` or a custom `UsrPhoneFormat`).
- `Binary` (a value stored as blob data, e.g. the logo) supports file upload and file readback (when the download tool is present; see below). Set the value with `update-sys-setting` using `value-file-path`: clio reads the file and Base64-encodes it locally, then sends it through the same `PostSysSettingsValues` path as every other type. (`create-sys-setting` has no `value-file-path`; its optional initial `value` accepts inline Base64 only, so for a blob value create the setting first, then upload with `update-sys-setting`.) Do NOT inline the Base64 in `value` for large blobs — a logo is thousands of tokens; pass the file path instead. Uploads honor the environment's file-security policy (`FileSecurityMode` + `FileExtensionsAllowList`/`FileExtensionsDenyList` + `AllowFilesWithUnknownType`): a blocked extension is rejected client-side, and while a policy is active an inline Binary `value` (which has no extension to check) is refused — use `value-file-path`. There is a per-value size cap (default 10 MB) enforced on both file and inline input. `list-sys-settings` lists Binary codes with `<binary>` values; `get-sys-setting` still returns an empty scalar for them. To save bytes, first discover `download-sys-setting-file` with `get-tool-contract`. When present, invoke it through `clio-run` with `environment-name`, `code`, and a required absolute `file-name` on the MCP server host. The destination includes the caller's filename and must be absent in an existing directory. Clio copies decoded bytes exactly: it does not infer MIME type, extension, or text encoding and does not parse JSON/XML. Text files uploaded as Binary work; ordinary Text settings are rejected. ClioGate is required. This download reads the effective current-user value with the platform's default fallback, unlike the scalar All-Users read. It returns `file-name`, `byte-count`, `exit-code`, and execution diagnostics, never Base64. Empty/invalid values and values above 10 MB fail without publishing a destination. Existing files are never overwritten. On older Clio versions where discovery reports no download tool, upgrade before using this flow; do not guess a different command.

Lookup resolution rules
- On `create-sys-setting` with `value-type-name=Lookup`, `reference-schema-name` is mandatory.
- On `update-sys-setting` for an existing Lookup, `value` may be a GUID **or** a display name from the referenced entity. Display names are resolved before save; ambiguous matches (two or more rows sharing the same display name) are rejected with a structured error — pass the record GUID instead to disambiguate.
- The current All-Users default returned by `get-sys-setting` for a Lookup is the GUID of the selected record, not the display name.

SecureText masking semantics
- Stored SecureText values are encrypted by the platform.
- Every MCP read path masks the value before surfacing it: `list-sys-settings` shows `"***"` in the catalog row; `get-sys-setting`, `update-sys-setting` read-back, and `create-sys-setting` read-back all return `"***"`.
- Unconfigured SecureText settings (no All-Users row) return an empty string so callers can still distinguish "has secret" from "no secret".
- Read-back ≠ stored value for SecureText. After `update-sys-setting` with `value-type-name=SecureText` the response says `"***"` even though the write succeeded. Treat `success: true` as proof of the write, not the response value.

Date / Time / DateTime caveat
- On environments where the platform `DataService` returns DateTime in server-local TZ, `Date` and `Time` settings may round-trip with a single-day or single-hour delta (for example input `2026-12-31` reads back as `2026-12-30` on a server-local `+01:00` deployment).
- This is platform behaviour reproducible from the legacy CLI path; it is not a tool defect. Account for it in expectations; do not retry-loop chasing the delta.

Input validation guarantees
- Sys-setting codes are validated against the Creatio identifier pattern (`^[A-Za-z][A-Za-z0-9_]*$`) before any platform request is issued. Codes with quotes, control characters, whitespace, or other special characters are rejected client-side with a structured error.
- The `value` field may contain arbitrary printable characters including quotes, backslashes, and Unicode. clio escapes the value safely before it leaves the process — pass the raw string as-is, do not pre-escape.

Verification discipline
- Read back after write when correctness matters: use `get-sys-setting` for a single code, `list-sys-settings` for catalog confirmation.
- The structured `success: false` envelope carries an explicit error message — read it before retrying.
- For SecureText writes, the read-back masking means the plaintext cannot be confirmed through `get-sys-setting`; trust `success: true` from `create` / `update` instead.

Anti-patterns
- Do not inline a large Binary blob (e.g. the logo) in `value`; pass `value-file-path` so clio encodes the file locally and the bytes stay out of the tool-call arguments.
- Do not expect a real `Binary` value from `get-sys-setting` / `list-sys-settings`; the row is listed for discovery but the value shows as `<binary>` (scalar get/list do not return Binary content).
- Do not call `update-sys-setting` for SecureText and then try to verify the plaintext through `get-sys-setting`. The response is masked.
- Do not retry Date/Time writes to "fix" a TZ delta on the read side; the platform-side conversion is consistent and orthogonal to the tool.
- Prefer the MCP `create-sys-setting` / `update-sys-setting` tools over shelling out to the legacy `clio set-syssetting` CLI through any shell-execution tool; the MCP path validates input, masks secrets, and returns structured errors.
