clio MCP core rules

Non-negotiable invariants. They apply to EVERY operation regardless of task; read them before
acting. Each is ALSO enforced on a guaranteed channel (the tool-result note, server-side
validation, or the Destructive flag), but you must still honor them proactively.

- After applying any guidance, reconcile it against observed behavior at the end of the task. Every `get-guidance` response carries the effective `feedbackPolicy`; follow it when the guidance is contradicted or requires a material deviation. Read `knowledge-feedback` for reporting, evidence, approval, privacy, and deduplication rules.

- compile-creatio is NOT needed after create-page/update-page/create-entity-schema/update-entity-schema/create-lookup/create-data-binding. For changed backend C# delivered as source, prefer compiling only the affected package; the mere presence of C# in a pushed package is not a reason to recompile unchanged or already-built code. Never compile or restart "just in case". After create-entity-schema/create-lookup the entity's OData controller (/0/odata/<Entity>) is rebuilt asynchronously (~1-2 min): a 404 from an odata-* tool right after creation is the expected async gap — wait and retry, do NOT compile or restart.
- Package compilation is the default for backend source changes in ordinary database-backed package deployment: push the source package/workspace, then run `clio compile-package <PACKAGE> -e <ENV>`. The MCP equivalent is `compile-creatio` with arguments `{"environment-name":"<ENV>","package-name":"<PACKAGE>"}`; it accepts exactly one package per call. Compile additional affected packages sequentially when dependencies require it. Exception: C# saved by `create-business-process`/`modify-business-process` (a Script Task, process methods) is compiled with `process-name` instead of `package-name` - on Creatio 10.x a package compile does not pick such a save up. Omitting `package-name` runs a full configuration compile: use that only for an identified configuration-wide requirement or evidence that package compilation is insufficient, never as an unconditional post-push chaser. File system mode (FSM) retains its own workspace-specific build/deploy rules (read `fsm-mode`); this sequence does not authorize `push-workspace` or database compilation in FSM.
- Precompiled delivery is a separate path: build the package for the target Creatio runtime and compatible platform dependencies, include the built binaries in the package, then install it with `push-pkg`. A .NET 8 assembly cannot be deployed as a .NET Framework assembly; do not assume any .NET build matches every .NET target. Rebuild for the actual target or deliver supported source for target-side package compilation. Do not automatically recompile a compatible precompiled package after installation; restart Creatio to load the newly installed DLL, then verify its behavior.
- Canonical DLL activation cycle: build/compile the affected package -> install it if built locally -> restart Creatio -> verify the changed backend behavior. After target-side package compilation completes, call `restart-by-environment-name` (CLI: `clio restart -e <ENV> --wait-ready`) to load the newly built DLL; apply this on .NET hosts as well as .NET Framework. Do not infer that compilation success or an internal reload has activated the new DLL. For precompiled delivery, restart after `push-pkg` completes. The MCP restart defaults `waitReady` to true: await readiness, then probe the changed endpoint/field/behavior and assert the new result. A successful build/install or a healthy site alone is not proof of the running assembly version. Do not restart while compilation or installation is running. This DLL activation rule does not require a restart for client-only edits that install no new DLL.
- Long-running tools (create-app, create-app-section, update-app-section, get-app-info, sync-schemas, compile-creatio, restart-by-environment-name) stream progress; a progress notification is NOT a timeout. Do not cancel or retry; read state with get-app-info / list-app-sections first. These progress-streaming reads are exempt from the read-response deadline below — await their completion. compile-creatio and restart-by-environment-name can additionally return exit-code 0 with an in-progress note (operation accepted, still running past the MCP response deadline) — that is NOT a failure and NOT grounds to retry: poll compile-status (compile) or restart-status (restart) instead. While a compile-creatio is running server-side, the Creatio core serializes compilation and rejects a second concurrent compile for the same environment, and the environment must not be restarted mid-compile: after launching compile-creatio, wait and poll compile-status — do NOT start another compile-creatio or restart-by-environment-name for that environment until compile-status reports completion.
- Read-only / retry-safe tools (list-pages, list-apps, list-app-sections, get-page, …) are bounded by a response deadline (default 120s, override CLIO_MCP_READ_DEADLINE_SECONDS). If one exceeds it you get a structured result with error-class=creatio-timeout and read-response-timed-out=true: the read did not finish (a busy stand), NOT a failure of your input. It is non-destructive and safe to retry — wait briefly and retry, optionally with a narrower filter / smaller limit. This differs from the write timeout (section-created=in-progress), where you must poll and must NOT retry.
- Captions use the connected user's profile culture: call get-user-culture once per session (re-detect when the environment changes) and reuse it. The en-US entry must hold English text; a non-Latin caption under en-US is rejected. If it fails, ASK the user; never assume the host locale.
- Destructive tools (uninstall-creatio, clear-redis-db, stop-creatio, delete-*) are high-impact: confirm the target environment with the user first.
- compile-creatio is a HEAVY, high-impact operation: even package-scoped compilation can force a runtime reload that affects EVERY user connected to the environment. Before EVERY compile-creatio call (every time, NOT once per session), warn the user that compilation is heavy and may disrupt active users, then ask whether to compile now or postpone. A repeated or explicit user request to compile ("compile this again", "just compile it") is NOT itself this confirmation, and a warning shown or answer given earlier in the session is NOT standing consent — re-ask proceed-or-postpone before every compile, INCLUDING an identical repeat of the same request in the same session. If the user postpones, do NOT call compile-creatio and tell them it can be run later (ask you again when ready, or run the selected scope themselves: `clio compile-package PACKAGE -e ENV_NAME` for a package, and `clio compile-configuration -e ENV_NAME --all` only when full compilation was justified). Only call compile-creatio after the user confirms; a confirmed compile then runs exactly as before.
- uninstall-creatio may complete with a WarningMessage, a warning stage, and a success-with-warnings terminal when Windows cannot remove a locked IIS application-pool profile or dbHub live verification is unavailable (exit code 0 / IsError=false); show the warning detail, but do not retry the destructive command. The conditional remove-dbhub-source stage runs only after destructive cleanup and before unregister; an earlier failure skips it and retains the source for reconciliation.
- uninstall-creatio preserves an application pool and its Windows profile when another IIS application still uses that pool; a skipped profile stage in this case is expected and requires no manual cleanup. Recorded IdentityService attachment and standalone/combined removal rules live in `docs://mcp/guides/operations/deploy-lifecycle`; read that guide when an identity component is attached.
- uninstall-creatio resolves a named target from the environment's registered `EnvironmentPath`, not its URI. It requires a complete, unfiltered IIS inventory, resolves existing filesystem aliases, removes every safely validated site or application with that physical directory identity (including classic nested `/0` applications), and handles every pool assigned to the selected applications while preserving pools shared with unrelated applications. Operations using the same environment name or physical directory are serialized, and unregister succeeds only while the registered path still matches. Incomplete IIS discovery is a hard failure before database or file deletion. If a complete inventory has no matching target, it continues as a local non-IIS uninstall. A missing, relative, environment-variable-based, or filesystem-root `EnvironmentPath` is also a hard failure: do not infer a filesystem path from IIS bindings or the environment URI.
- Leave NO scratch behind: any probe or throwaway artifact you create while working a solution out — a business process, a page, a lookup, a schema, a test record — is deleted from the environment before you report the task done. A stand carrying half-built artifacts from an exploration is indistinguishable from a broken environment to the next person who opens it. Deleting one is itself a destructive operation: confirm the target with the user the same way.
- Every response carries a correlation-id; on error, inspect the inner-exception chain.
- Guidance is versioned: every `get-guidance` response carries the `libraryVersion` that produced it. Quote that value when you report a guidance defect or compare an outcome with another machine — two agents can be served different generations of the same article, and the version is the only thing that distinguishes them.
- Product telemetry applies to EVERY agent-driven Creatio workflow you run here, not only app creation, and an agent is in scope EVEN WHEN NO SKILL FILE IS LOADED. Skip it only for non-agent use (a plain script, a CI job). It must never gate, delay, or alter the developer's task. Read `get-guidance name=product-telemetry` before your first event: that guide owns the stage vocabulary, the `workflow` field, the consent flow, and what a rejected event means.
- Resident tools (get-tool-contract index: resident=true) are called natively; every other tool is invoked via clio-run <command>. Never wrap a resident tool in clio-run. Naming a non-resident tool directly still works for READ-ONLY tools; any tool that WRITES answers with code confirmation-required and a retry shape instead of executing — re-send it through clio-run as that shape says. This applies to additive-only writes (for example odata-create) too, so a confirmation-required outcome does NOT mean the tool is destructive: read the destructive field in the payload.
- Navigation placement is decided BEFORE you create an app, not after. `create-app` puts the new section in the `My applications` workplace, which is granted to `System administrators` only, so an app built without asking is an app ordinary users cannot open. When the request does not name a target workplace, ask in the SAME turn you ask about the environment - before `create-app`, not after the pages are built: which workplace the section AND its home page belong to (offer a NEW workplace named for the app and recommend it when scaffolding), and which roles should see it. Read `get-guidance name=workplaces` for the option set and the write recipes. Asking late is not equivalent: it makes the user re-decide work you already did.
- Verification in browser preference (any task where you would verify a create/change): after a tool reports success, do NOT automatically open a browser, Playwright, or navigate the app to confirm the result. Read your saved "verification in browser" preference from persistent memory - automatic (you open the app and check) or manual (the user checks). If none is saved, ask the user once and persist the answer so future work does not re-ask; if you cannot persist it, honor the choice for this session. On manual, briefly tell the user what to check instead of opening a browser. Machine read-backs a guide already prescribes (for example get-page, validate-page) are NOT browser verification - keep doing them regardless.

- General Creatio record operations use DataService first (ESQ reads and native entity writes). Resolve available contracts first: use execute-dataservice-batch for explicit-record writes when installed. On older clients without a suitable write contract, existing OData write recipes remain a supported fallback; report that capability limitation. Prefer a dedicated native lifecycle tool when one owns side effects. OData is a justified fallback only when the required operation has no suitable DataService/native path; state the reason. Read `sequences` for Sales Engagement lifecycle operations and `esq` for query construction.
