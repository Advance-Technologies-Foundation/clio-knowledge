clio MCP app-modeling-details guide — failure handling, rare schema edits, and the evidence behind the app modeling rules

A details article of the application guide set, reached through `app-modeling`, which points here and is read first.
This article is the authoritative owner of what each `create-app-section` `error-class` means (`app-modeling` owns how to handle each one), why sections in one app are created one at a time, the `sync-schemas` retry and resume behavior, the rare schema edits (primary-display column, relabeling an inherited column, redirecting an inherited lookup, `Color` columns), the Git-first capture rule's `export-schema` and tool-contract clauses, and the evidence, timings and reasoning behind the `app-modeling` rules. Split out of `app-modeling`, which keeps every rule needed on the common path of creating an app with its sections, entities and pages; read that first.

Core contract
- Why the navigation gate exists: `create-app` registers the section in the `My applications` workplace, which most users cannot see, so without the user's placement decision the app is not where users expect it.

Preferred workflow
- `sync-schemas` retry and resume: it retries transient network faults (DNS / reset / timeout / gateway) per operation and, on a mid-batch abort, returns a `resume-plan`. Because the schema operations are convergent, re-submitting the whole batch verbatim is safe for the SCHEMA operations only — they replay as `already-satisfied` / `reconciled`. When the batch includes `seed-data` or a `resume-plan` was returned, resubmit `resume-plan.operations` instead: `seed-data` is NOT replay-safe for rows without a `Name`, and the plan converts a post-create seed failure to a standalone op.

Application modeling guardrails
- The default section `create-app` creates is a record in `ApplicationSection`; it is not in the response manifest.
- Generated pages' default content: the auto-generated `{code}_FormPage` starts with `{prefix}Name` pre-inserted in `SideAreaProfileContainer` and Feed + AttachmentList tabs; the auto-generated `{code}_ListPage` starts with `{prefix}Name`, `CreatedOn`, `CreatedBy` as default DataTable columns (`{prefix}` is the response's `schema-name-prefix`). With `with-mobile-pages: false`, `create-app` leaves three web pages: `{code}_FormPage`, `{code}_ListPage`, `{code}_Detail`.
- Section code derivation: caption `Customer Profile` becomes entity `UsrCustomerProfile` when the prefix is `Usr`, or `AbcCustomerProfile` when it is `Abc`.
- Why sections in one app are created one at a time: each `create-app-section` is a long (~90–100 s) backend insert, so overlapping inserts against the same app contend server-side and abort with a detail-less `InsertQuery failed`. clio serializes creations per app in-process and auto-retries a detail-less rejection once with verification; the sequential rule in `app-modeling` still applies.
- Why a section list placeholder is waited out first: on the `create-app-section` path the usual cause is load latency, not the viewport — the generated grid sits at the top of the page, and was still empty ~20 s after load and full by ~45 s (Creatio 10.0.0.934, .NET Framework). Hence the order in `app-modeling`: wait for the `SelectQuery`, and only if it never appears bring the grid into its scroll container's viewport.
- What a failed `create-app-section` reports, per `error-class`; `section-created` reports the side-effect state (`true` / `false` / `unknown` / `in-progress`). `app-modeling` owns what to do about each class.
  - `transport` — the request never reached Creatio, so nothing was created.
  - `creatio-timeout` — Creatio produced no response within the budget, and the section may still be created server-side. With `section-created: in-progress` the creation exceeded the response deadline but is still running server-side on the long-lived clio MCP server.
  - `contention` — the insert was aborted without a detailed reason. The server returned no detail, so this may be parallel creation in the same app OR a server-side rejection unrelated to concurrency. No section was created (verified); clio already serializes creations per app and auto-retries a detail-less rejection once, which is why a sequential create that still fails points at the server rather than at concurrency.
  - `server-error` — Creatio rejected the operation with a real, detailed reason.
- `Date` / `Time` alias evidence: date-only and time-only intent is not preserved in the schema type. On Creatio 10.1.585.0 (.NET 8, PostgreSQL) in September 2026, `Date` and `Time` columns written through `sync-schemas` read back as `DateTime`; the `sync-schemas` contract states the alias from clio 8.1.0.127.
- Rare schema edits:
  - Primary-display column (the value shown in lookups and links): call `set-entity-schema-properties` with `primary-display-column` (an own or inherited column, resolved by name), and read it back via `get-entity-schema-properties` (`primary-display-column-name`). This is the only supported way to change the display column of an existing schema.
  - Relabeling an inherited column: to rebrand a base/inherited object without redefining columns (e.g. relabel a replacing schema's inherited fields), override just the caption/description of the inherited column through `modify-entity-schema-column` / `update-entity-schema` `title-localizations` / `description-localizations`. The override lives on the child schema and leaves the parent unchanged; an inherited column's name, type, and flags stay read-only and it cannot be removed. A lookup's reference schema is the one exception, in the next item.
  - Redirecting an inherited lookup (clio <CLIO-INHERITED-LOOKUP-OVERRIDE-TBD> or later): when the parent declares a lookup the new schema must point at its own counterpart — for example `Folder` (-> `BaseFolder`) of a `BaseItemInFolder` child, which MUST reference the entity's folder schema (a schema created from `BaseFolder`, such as `ContactFolder` for `ContactInFolder`) — create the target first, then redirect the inherited column; do NOT add a column of the same name, which is refused naming the parent. In `create-entity-schema` send the column as `{"name":"Folder","override":true,"reference-schema-name":"<Entity>Folder"}`; it may add `title-localizations` and nothing else (`type`, `required`, defaults and `masked` are refused). On an existing schema use `modify-entity-schema-column` or an `update-entity-schema` `modify` with `reference-schema-name`. clio refuses before saving when the parent is not virtual, the schema replaces its parent, the target is missing or virtual, or the target does not inherit from the column's current reference schema, and reads the reference back after saving. Evidence: on Creatio 10.2.473.0 (MSSQL) in October 2026 the stock `ContactInFolder` keeps `Folder` inherited from `BaseItemInFolder` with its reference changed to `ContactFolder`; the same request saved through clio read back with no own column; Creatio dropped such a change for a non-virtual parent or a replacing schema without an error, and saved `Folder` -> `Contact` without checking the hierarchy, which is why clio checks both. An older clio ignores `override` and cannot redirect the column.
  - `Color` columns (a swatch/hex value such as `#RRGGBB`): `create-entity-schema`, `modify-entity-schema-column` and `sync-schemas` accept the `Color` type. `Color` is not a text column: the text-only options (multiline / accent-insensitive / format-validated / masked) do not apply to it, and `get-entity-schema-properties` reads it back as the named `Color` type.

Git-first workspace: capture DB-first schemas before pushing
- `export-schema` is useful for a separately reviewable single-schema transfer, but its standalone bundle is consumed by `import-schema`; merely exporting it does NOT update the workspace package or make a subsequent `push-workspace` safe. Pull the affected package before pushing it.
- Read installed tool contracts for current arguments and defaults. Do not assume ordinary schemas are parentless by default or that creation accepts only one column.
- Evidence and scope: a user report confirmed on clio 8.1.0.130 (September 2026) that this ordering is still needed. As of clio 8.1.0.139, clio does not warn before `push-workspace` deletes DB-only schemas.
