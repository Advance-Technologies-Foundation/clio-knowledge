clio MCP existing-app maintenance guide
Moved to `existing-app-maintenance-details`: column-default round-trip fields, why merged column reads return unknowns, section-title language preservation, translations evidence (non-`en-US` profiles unmeasured), the full reuse example. Read it when you re-apply, remove or read back a column default, write a section title in another language or under a non-English profile, or a merged column read returns unknown flags. Section-creation failure background: `app-modeling-details`.

Canonical flow
- Prefer `discover -> inspect -> mutate -> verify` for minimal edits to an existing app.
- Discover the target app with `find-app`; fall back to `list-apps` only for a full unfiltered enumeration.
- Section flows in an existing app, each preferably starting `list-apps -> get-app-info`: create `-> create-app-section -> get-app-info`; update metadata `-> update-app-section`; list `-> list-app-sections`; delete `-> list-app-sections -> delete-app-section`. Delete removes the section ITSELF from every workplace; to take it out of ONE workplace and keep it elsewhere, use `get-guidance` with `name` set to `workplaces` instead.
- Prefer `list-pages -> get-page -> sync-pages -> get-page` as the canonical page workflow, including single-page saves when the caller wants the clio-advertised path.
- Read before write, and read back after mutations when the tool or workflow allows it.
- The application tools (`create-app-section`, `update-app-section`, `delete-app-section`, `list-app-sections`, `get-app-info`) are long-running calls streaming `notifications/progress`: await completion; progress is not a stall — do not cancel/retry or fall back to raw SQL or manual UI on a perceived client timeout.
- Other `get-guidance` names: `data-bindings` (data-binding workflow selection); `sys-settings` (seeding, listing or updating system settings); `dataforge-orchestration` (full DataForge protocol: layers 0–4, failure rules, stale index recovery).

Discover the target app
- Prefer `find-app` with `search-pattern` to map a partial app name (e.g. "Customer Request Management") to its real code (e.g. `CrtCaseManagementApp`) in one call; it matches name, code, description and section captions and returns each match with its sections. Omit the pattern to list all apps with their sections.
- Use `list-apps` when you do not yet know the installed application code or need to confirm candidates.
- Wrap MCP tool arguments under the top-level `args` object exactly as the tool schema advertises (e.g. `{"args": {"environment-name": "...", "code": "..."}}`); do not flatten or rename canonical fields.
- Use `get-app-info` after `list-apps` to confirm the primary package and entity context for the target app.
- The `get-app-info` response includes `schema-name-prefix` — the active SchemaNamePrefix. Use it as the prefix for ALL new schema codes in the session (entity, column, page schema, lookup and binding names). Empty means no prefix. Do not assume `Usr`.
- If no `get-app-info` has been called yet and you need to name a schema artifact (entity, lookup, page, column), call `get-schema-name-prefix` first.
- Use `create-app-section` for "add a new section to this existing app", and `update-app-section` for "change metadata of this existing section", including fixing a broken JSON-style heading with a new plain-text caption.
- If `create-app` fails because the app or configuration already exists, switch to this flow: `list-apps`, `get-app-info` with the matched identifier, then inspect → mutate → verify.
- `create-app-section` takes `application-code` as the target-app selector and is scalar-only: `caption`, `description` and `entity-schema-name` as top-level strings, `with-mobile-pages` as a top-level boolean.
- Omitting `entity-schema-name` makes Creatio derive both the section code and the new entity code from the caption ("Customer Profile" → "{prefix}CustomerProfile", {prefix} = the active SchemaNamePrefix): choose the caption that yields the desired entity name.
- Do not send `title-localizations`, `description-localizations`, `caption-localizations`, or `name-localizations` to `create-app-section` or to `update-app-section`.
- When reusing an existing entity schema, provide `entity-schema-name`. Otherwise omit it and let Creatio create a new object for the section.
- Create sections in one application SEQUENTIALLY: create one, await it, then the next. Do not fan out parallel `create-app-section` calls against the same app — they abort with a detail-less `InsertQuery failed` (clio serializes per app and retries once).
- When `create-app-section` fails, read `error-class` first, follow the returned `retry-guidance`, and never blind-retry the same call. `section-created` reports the verified side effect (`true`/`false`/`unknown`).
  - `transport`: the request never reached Creatio; retry is safe.
  - `creatio-timeout`: the section may still be created server-side; wait, run `list-app-sections`, and retry only if it is still absent.
  - `contention`: aborted without detail (parallel creation OR an unrelated server rejection); no section was created (verified). Confirm with `list-app-sections`, create one at a time; if a single sequential create still fails, treat it as server-side (`clio healthcheck`, Creatio server logs) rather than just retrying.
  - `server-error`: Creatio rejected it with a real, detailed reason; fix inputs or server state first.
- `update-app-section` takes `application-code` and `section-code` as the selector pair and is a partial scalar update: pass only the top-level fields that change — `caption`, `description`, `icon-id`, `icon-background` (`caption-culture`: Translations below).
- If the target package already contains a supporting or link schema that models the required relation pair, reuse it. Do not create a synonym schema just because the requirement uses a different business caption (an existing `UsrSupportCaseKbLink` serves a Related Knowledge detail on Support Case: do not create `UsrSupportCaseKnowledgeBase`).
- Treat "add a tab/detail/grid that shows linked records" as a page-only/object-model reuse task by default. Create a new schema only when the inspect phase finds no suitable existing backing schema.

Inspect pages before editing
- Use `list-pages` to discover candidate Freedom UI page schemas in the target package or by installed `code`; each item carries `schema-name`, `uId`, `packageName` and `parentSchemaName`.
- Use `get-page` to inspect the merged page bundle and retrieve the raw editable page body.
- For a page's WHOLE replacing-schema chain (every ancestor's own body, e.g. Classic->Freedom migration discovery), call `get-page-hierarchy` via `clio-run` ONCE instead of `get-page` / `get-client-unit-schema` per schema (`metadata-only` for a light listing, `offset`/`limit` to page a very large chain).
- For writes, send the full `raw.body` string back to `sync-pages` or `update-page`; do not send `bundle` or `bundle.viewConfig` as the body payload.
- Use `get-component-info` when `get-page` shows unfamiliar `crt.*` component types before editing nested config or child collections.
- For standard data-bound form fields, bind `control`/`value` directly to `$Name` or `$PDS_*`; prefer caption = `$Resources.Strings.<bindingAttribute>`, the SAME attribute the control binds to, with a DS-bound `modelConfig.path` (e.g. `$Resources.Strings.PDS_UsrStatus` for `$PDS_UsrStatus`), provided from the bound column. A bare column code is NOT auto-provided unless it equals the attribute name; on `operation:"insert"` a label neither the binding-attribute key nor registered is rejected.
- Do not route standard field bindings through proxy attributes (duplicating an already-DS-bound attribute under another name, e.g. `$UsrStatus` over `PDS.UsrStatus`); a plain `$UsrName` bound directly to a DS column is valid.
- Reserve `Usr*_label` and `Usr*_caption` resource keys for custom standalone UI with explicit `resources`; do not use them as datasource field captions.
- When a page tool needs `resources`, pass a JSON object string rather than a nested object payload.
- Absence of a tab, detail, or grid on the page does not prove the backing entity is missing. Resolve the backing schema from runtime app context before planning new schema work.

Inspect schema before editing
- Use `get-entity-schema-properties` before planning a schema mutation, WITHOUT `package-name`, to read the merged/effective schema (columns from ALL packages); custom columns often live in a package other than the defining one.
- Do NOT treat an empty column list (or `own-column-count: 0`) from a single-package read as proof a column is missing: re-read without `package-name`, or use `find-entity-schema` to find the customizing package, before concluding a field must be created.
- For a change scoped to one existing column, first call `get-entity-schema-column-properties` WITHOUT `package-name` to discover its effective metadata across ALL packages.
- Merged column mode returns `track-changes`, `localizable-text` and `do-not-control-integrity` as `null`: never interpret those unknown values as `false`. In merged mode `source` means inheritance from a parent entity schema; it does NOT identify the owning package.
- When one of those values or package-layer ownership must be authoritative, list the layers with `find-entity-schema` (schema layers, not a column's owner), then call `get-entity-schema-column-properties` WITH each candidate `package-name` until the defining layer is found; it returns that layer's full designer metadata.

Preferred minimal mutations
- Use `sync-pages` as the canonical page write path after editing the raw body returned by `get-page`. Keep `update-page` only for single-page dry-run or legacy save workflows.
- Use `modify-entity-schema-column` for a single-column change when the target schema and column are already known.
- Use `sync-schemas` when the work spans multiple ordered schema steps, mixes create/update/seed operations, or must stay batched. Requests and responses use `operations[*].type`; do not send `operations[*].operation`.
- `sync-schemas` `create-lookup`, `create-entity` and `update-entity` are convergent: a schema already in the target package is reconciled (only missing columns added; unnamed columns untouched), never recreated. `outcome` per operation: `created`, `reconciled`, `already-satisfied` are successes; `collision` is `success: false` + `collision-info` — a same-name schema in a DIFFERENT package (a `create-entity` `extend-parent: true` replacement is `created`) or a same-package schema with an incompatible parent/kind. Resolve the real conflict before retrying.
- `sync-schemas` retries transient network faults per operation and returns a `resume-plan` when a batch aborts mid-way. Re-submitting the whole batch verbatim is safe for SCHEMA operations only; when it includes `seed-data` or a `resume-plan` was returned, resubmit `resume-plan.operations` instead — `seed-data` is NOT replay-safe for rows without a `Name`.
- The column shape `get-app-info` returns round-trips into `sync-schemas update-entity` without translation: send a read column back in an `update-operations` entry with an added `action` (`modify`/`remove`); to add columns, put read/create-shape objects in its `columns` array (no `action`; scalar `caption` becomes `title-localizations`), an implicit add-batch. A read may carry read-only fields the write path ignores (e.g. `resolved-value-source`); do not read an extra field as drift.
- A column default (`default-value-config`): send it back as-is to re-apply it; to remove it, REPLACE the object with `{"source": "None"}` — do not just flip `source`: `None` with any surviving `value` / `value-source` / `sequence-*` field is rejected. To build a lookup default, follow `get-guidance` with `name` set to `app-modeling`. Trust the field's absence only after `get-tool-contract` for `get-app-info` names `default-value-config` in its `entities` output (an older clio omits it for every column). Per-source fields to SEND: `Const` -> `value`; `Settings` / `SystemValue` -> `value-source`; `Sequence` -> `sequence-prefix` + `sequence-number-of-chars`. An absent field means no default (a stored `None` included).
- Treat `create-lookup`, `create-entity-schema`, `update-entity-schema`, `create-data-binding-db` and `update-page` as fallbacks for when the preferred batched workflow does not fit the requested scope.
- For standalone lookup seeding or local binding artifacts, follow `get-guidance` with `name` set to `data-bindings`. When that guide resolves to a DB-first binding path, prefer `create-data-binding-db` or `upsert-data-binding-row-db` over direct SQL commands.

Translations (other cultures)
- This section owns object, column and section titles in another culture. Page captions: `page-schema-translation`. Culture rules (absent or inactive culture): `localizable-values`.
- MUST call `get-tool-contract` for `update-app-section` before ANY update of an existing section and before using `caption-culture`. Creatio deletes the section title and description in every non-default language on EVERY section update, even an icon-only one. When the contract lists `caption-culture`, clio preserves those languages and the result lists them. When it does not, `caption-culture` is silently ignored, `caption` overwrites the profile-culture (English) title with success reported, and any update deletes the other languages: translate the section title in the native designer and do not update a translated section with that clio.
- Section title, when the contract lists `caption-culture`: send `caption` with `caption-culture` (for example `es-ES`), one language per call; only that language changes. `description` stays in the profile culture.
- Object or column title: send `title-localizations` with the new culture — `set-entity-schema-properties` for the object, `modify-entity-schema-column` / `update-entity-schema` (or `sync-schemas`) for a column. A column map must also carry the current `en-US` value, re-sent unchanged; unsent cultures are preserved. The title shows on every page, list and app using the object: change only objects created in the app's own package (not a replacing schema of another package's object); for another package's object, list the titles and ask the user.
- Right after creation a non-`en-US` title is not blank, yet not translated (`localizable-values`): translate each target culture explicitly. Readback: `set-entity-schema-properties` compares the object title in every culture it writes and fails on a mismatch; the column tools check only that the column exists (an inherited column also its profile-culture title): check a column title in the target culture yourself, in the object designer or the UI (`core-rules` verification-in-browser preference).
- A DS-bound field label on a page is the column title: translate the column, not the page.

Verification
- `sync-pages` keeps client-side validation on by default; enable its `verify` only for read-back within the same call (default `false`). After `update-page` or `sync-pages`, read the page again with `get-page` when you need explicit read-back.
- After `modify-entity-schema-column`, re-read the column with `get-entity-schema-column-properties` or the full schema with `get-entity-schema-properties`.
- After `create-app-section`, refresh app context with `get-app-info` when you need the updated primary-package entities and pages; `update-app-section` already returns the previous and updated metadata, so a separate read is optional unless broader app context is needed.
- After `sync-schemas`, refresh with `get-app-info`, `get-entity-schema-properties`, or both. The refresh is essential: it verifies the changes materialized, updates the canonical main-entity selector, and detects incomplete states such as `Database update required`. Treat the batch as successful only when refreshed metadata is available and no schema is left incomplete.

Section deletion safety
- Before using `delete-app-section`, inspect its live tool description: a fixed implementation explicitly says it uses declared page UIds and never a name prefix. Before clio 8.1.0.132 it can delete unrelated schemas sharing the section code prefix. If that guarantee is absent, do not use the command; upgrade to clio 8.1.0.132 or later or have the application owner remove individually identified artifacts with a verified backup.
- The fixed flow removes only the section's declared list/form pages — keeping pages shared by another section or registered as edit, mini or search-row pages, and the form page while its entity stays — and keeps the entity by default; `delete-entity-schema` is a separate irreversible opt-in, and a shared entity is refused. Never infer the entity name from the section code.
- Auxiliary artifacts without a declared section link (details, mobile pages, addons, listeners) are retained, not guessed from their names: inspect them separately; a successful section removal does not mean every generated artifact was removed.
- Deletion is not transactional: a reported failure may follow earlier successful deletions. Review the logged schema identities and check section discovery, neighboring schemas and data afterwards; inspect actual state before retrying; never interpret a partial run as success.
