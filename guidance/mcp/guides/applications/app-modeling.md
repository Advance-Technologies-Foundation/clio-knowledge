clio MCP app modeling guide
Moved to `app-modeling-details`: what each `create-app-section` `error-class` means; `sync-schemas` resume rules; rare schema edits (display column, relabeling an inherited column, `Color` columns); the Git-first rule's `export-schema` and tool-contract clauses; the generated pages' default content; the evidence, timings and reasoning behind these rules. Read it when `create-app-section` fails, a `sync-schemas` batch aborts, you make one of those schema edits, or you capture schemas into a Git-first workspace.

Profile language (detect once, reuse, ask on failure)
- Before creating ANY entity (application, object, page, section, lookup, column), call `get-user-culture` ONCE per session to detect the profile language. Reuse it for all names, labels and captions; do not re-detect per entity (the server caches it per environment), only when the active environment changes.
- The detected culture is the LANGUAGE OF THE CAPTION TEXT, not just the localization key: write every name, label and caption IN it. Do NOT keep captions in the conversation/task language when it differs — the profile language wins (or ask the user): an `en-US` profile means English captions ("Number", "Equipment") even for a request written in Ukrainian.
- The mandatory `en-US` localization-map entry MUST contain ENGLISH text; NEVER put non-English text (e.g. Cyrillic) under `en-US`. For a non-English profile add a second entry under the profile culture key (e.g. `uk-UA`) AND keep `en-US` as the English baseline. clio REJECTS a caption whose script does not match a Latin-script culture key — fix the language or move the text under the matching key.
- If `get-user-culture` returns `success:false`, ASK the user which language to use before creating anything. Do NOT silently fall back to the host machine locale or to `en-US`.
- To force a language for one creation, pass `caption-culture` (precedence: `caption-culture` > detected profile culture > `en-US`). On `create-app-section` it only selects the readback language; for `update-app-section` see `existing-app-maintenance`.

Core contract
- clio MCP is a stdio MCP server, not an HTTP or browser API. Use discovered tool names exactly as advertised; newer design tools use kebab-case argument names (`environment-name`, `package-name`, `schema-name`).
- `get-guidance` names: `existing-app-maintenance` (existing-app minimal edits), `data-bindings` (data-binding workflow), `sys-settings` (seeding or reading system settings), `dataforge-orchestration` (full DataForge protocol).
- Navigation placement and audience: follow the Navigation placement rule in `core-rules` before `create-app`.

Discovery before invocation
- Always read `get-tool-contract` before the first invocation of any MCP tool in a workflow (exact parameter names, aliases, required fields, defaults, response shapes).
- Wrap arguments under the top-level `args` object exactly as advertised (`{"args": {"code": "..."}}`); do not flatten or rename canonical fields.
- Never guess tool-specific identifiers: e.g. `get-app-info` and `list-pages` use `code`, `get-app-info` uses `id`, `create-app` accepts `icon-background`, `create-app-section` accepts `application-code`, `update-app-section` accepts `application-code` plus `section-code`.
- Call `get-schema-name-prefix` when you need the SchemaNamePrefix before `create-app` (existing app, names planned upfront); a first `create-app` call already returns `schema-name-prefix`.

Preferred workflow
- The application tools (`create-app`, `create-app-section`, `update-app-section`, `delete-app-section`, `list-app-sections`, `get-app-info`) are long-running and stream `notifications/progress`. Await completion — progress is not a stall; do not cancel/retry or fall back to raw SQL or manual UI on a perceived client timeout.
- `create-app` models a new app shell; `create-app-section` adds a section to an existing installed app; `update-app-section` changes an existing section's metadata instead of creating one.
- Prefer `sync-schemas` for multi-step schema work and `sync-pages` for multi-page saves; single-tool entity or page mutations are fallbacks for a task truly limited to one column, one lookup, or one page save.
- Canonical flows: new-app entity `create-app` -> `sync-schemas` -> `get-app-info`; existing-app section `list-apps` -> `get-app-info` -> `create-app-section` -> `get-app-info`; section update `list-apps` -> `get-app-info` -> `update-app-section`; section discovery `list-apps` -> `get-app-info` -> `list-app-sections`; section delete `list-apps` -> `get-app-info` -> `list-app-sections` -> `delete-app-section`.
- Prefer `find-app` as the existing-app flows' front door when mapping an imprecise name to a code: it searches app name/code/description and section captions and returns apps WITH their sections, usually replacing `list-apps` + `list-app-sections`.
- Before deleting a section, follow the deletion safety rules in `existing-app-maintenance`; older implementations can delete unrelated prefix-sharing schemas.
- `create-app` runs Data Forge enrichment itself (optional `dataforge` diagnostics); do not require an external Data Forge preflight. Degraded Data Forge still yields the shell, with warnings and coverage flags.
- `sync-schemas` operations are identified by `operations[*].type` in requests and results; never send `operations[*].operation`.
- `sync-schemas` `create-lookup`, `create-entity` and `update-entity` are convergent: create-if-absent, else reconcile the missing delta (extend, never recreate), so re-running the schema operations is safe (`seed-data` is not). When a schema already exists, model an extend/reconcile step, not a synonym create.
- After a mid-batch `sync-schemas` abort, resubmit `resume-plan.operations` (not the batch) whenever a `resume-plan` came back or the batch had `seed-data` — `seed-data` is NOT replay-safe.
- Virtual entity (no physical table): read `virtual-entities`; the object MUST be created (`is-virtual: true` on `sync-schemas` `create-entity` or `create-entity-schema`; default false) and its saved `is-virtual` flag read back (`get-app-info` / `get-entity-schema-properties`) before its `IEntityQueryExecutor` is implemented.
- Page flow: `list-pages` -> `get-page` -> `get-component-info` when needed -> `sync-pages` or `update-page` -> `get-page` when read-back verification is required.
- Entity-schema mutations are DB-first: a schema is usable right after a successful schema call, without compiling.

Application modeling guardrails
- Use the `schema-name-prefix` value from `create-app` (or from `get-schema-name-prefix`) as the prefix for ALL custom schema codes in the session (lookups, entity columns, supporting entities, page names, business-process codes). An empty `schema-name-prefix` means no prefix — do not add one. Default Creatio environments return `Usr`.
- Anti-duplication: extend the canonical main entity `create-app` returns for the primary record type, never a synonym entity. Reuse a supporting or link schema that refreshed app context already exposes with the same purpose and relation pair; a synonym one in the target package is a blocker-level planning error. Captions are not naming authority: reuse the schema code runtime context maps a caption to.
- `create-app` creates: a package named after `code`; the app record; one default section wiring the canonical main entity to navigation; that entity (schema code = `code`) with one column `{prefix}Name` (MediumText; `Name` when the prefix is empty); pages `{code}_FormPage`, `{code}_ListPage`, `{code}_Detail`, `{code}_MobileFormPage`, `{code}_MobileListPage`. Read the response manifest (`entities`, `pages`; for the section use `canonical-main-entity-name`) instead of re-discovering.
- `with-mobile-pages` (top-level boolean, default `true`) creates the two mobile pages; for a web-only plan proactively pass `false`. An explicit `client-type-id` takes precedence.
- `create-app` is scalar-only (`name`, `description`, `optional-template-data-json.appSectionDescription` as plain strings) and requires `template-code` — the technical name such as `AppFreedomUI`, not a display label. Omit `icon-background` unless the request names an app color, which must then be one of: #A6DE00, #20A959, #22AC14, #FFAC07, #FF8800, #F9307F, #FF602E, #FF4013, #B87CCF, #7848EE, #247EE5, #0058EF, #009DE3, #4F43C2, #08857E, #00BFA5. Do not send `title-localizations`, `description-localizations` or `name-localizations`.
- `optional-template-data-json.entitySchemaName` needs `useExistingEntitySchema=true` and an entity that ALREADY exists (verify, e.g. `dataforge-find-tables`), else the server errors; for a new entity omit `optional-template-data-json`. clio rejects `useAIContentGeneration` there.
- MOBILE PAGE EDITING — STOP. On `schemaType: 10` from `get-page` (`schema-type: "mobile"` in `list-pages`), call `get-guidance` name `mobile-page-modification` before editing the body. Mobile pages are plain JSON (NOT AMD define(...)) with their own component registry and must NOT contain handlers, validators, or converters; web patterns break them.
- The generated form and list pages start with defaults (`{prefix}Name` on both); replace or extend them, and always `get-page` the current body before writing.
- `create-app` already creates the main entity's section — no `create-app-section` for it and no synonym section for the primary record type. `create-app-section` is only for an additional section backed by a new, separately named entity, whose code Creatio derives from `caption` (`Customer Profile` -> `{prefix}CustomerProfile`).
- `create-app-section` requires `application-code`; `caption`, `description`, `entity-schema-name` are plain strings, `with-mobile-pages` a top-level boolean; no `title-localizations`, `description-localizations`, `caption-localizations` or `name-localizations`. With `entity-schema-name` it reuses that entity; otherwise omit it and Creatio creates one.
- Create sections in one app SEQUENTIALLY — create one, await it, then the next; never fan out parallel `create-app-section` calls against the same app.
- A section list showing only `crt-data-grid-placeholder` right after `create-app-section` is still loading: do not re-create the section, re-compile, or restart — wait for the `SelectQuery` on the section entity (poll tens of seconds; only if it never comes, bring the grid into its scroll container's viewport). `related-list` owns the verification rule ("Verifying a list in the browser"), including when the placeholder IS a real failure.
- When `create-app-section` fails, read `error-class` and `section-created`, follow the returned `retry-guidance`, and never blind-retry the same call: `transport` — retry is safe; `creatio-timeout` — `list-app-sections`, retry only if the section is absent; `contention` — confirm it is absent, create sequentially; if a sequential create still fails treat it as server-side (`clio healthcheck`, server logs) rather than just retrying; `server-error` — fix inputs or server state first. Class meanings: `app-modeling-details`. `section-created: in-progress` is NOT a failure — do NOT retry (duplicate section) or build its pages with `create-page` / `sync-pages` (not registered as its List/Form pages); wait, then poll `list-app-sections` and `get-app-info` until the section and its `<Code>_ListPage` / `<Code>_FormPage` appear.
- Before updating an existing section, follow the `get-tool-contract` MUST in `existing-app-maintenance`: on a clio without `caption-culture`, any update, even icon-only, deletes the section title in other languages. `update-app-section` takes `application-code` + `section-code` and changed fields only (`caption`, `description`, `icon-id`, `icon-background`) as top-level scalars; no localization maps (section-title translation: `existing-app-maintenance`).
- Localized entity or column captions: create the app first, then apply them via `sync-schemas`, `create-entity-schema` or `update-entity-schema`.
- Entity-schema write tools take explicit maps: captions in `title-localizations`, column descriptions in `description-localizations` (never a scalar `description`). `title-localizations` is OPTIONAL on a column add (`en-US` derived from a scalar title/caption or the name); a provided map must include `en-US` in ENGLISH. Prefer it over legacy scalar `title`/`caption` (en-US fallback for an add only).
- Status/type catalogs: `create-lookup` or `sync-schemas` `create-lookup`. It always uses `BaseLookup`; `Name` (display field) and `Description` are inherited — add no duplicate title-like columns.
- Lookup seeding and binding artifacts: follow `get-guidance` name `data-bindings`, not consumer-repo notes. Outside `sync-schemas`, seed rows via `create-data-binding-db` or `upsert-data-binding-row-db`, not direct SQL helpers.
- Unknown lookup GUID in a binding row: call `dataforge-find-lookups` (`schema-name` = reference schema, descriptive query) before `create-data-binding`, `create-data-binding-db` or `upsert-data-binding-row-db`; use the best match's `lookup-id`. Uncertain `reference-schema-name` for an `update-entity-schema` Lookup column: confirm with `dataforge-find-tables` first.
- Seed rows create data only; "defaults to New" still needs an explicit `schema default` or `ui default`.
- A Lookup default to a seeded value needs separate calls (the GUID exists only after creation): (1) create and seed the lookup via `sync-schemas`; (2) resolve the row GUID via `dataforge-find-lookups` (`schema-name` = lookup entity, plus a descriptive query term); (3) apply it via `modify-entity-schema-column` or a `sync-schemas` `update-entity` with `default-value-config` source=Const, value = the GUID. Never skip step 2 — the default is the GUID, not the display name.
- Keep semantic types `Email`, `PhoneNumber`, `WebLink` (and `Color` for a swatch/hex value), not `ShortText`; they drive validation and component selection.
- Image/photo fields (`crt.ImageInput`): `ImageLookup` ("Image link"), NOT binary `Image`; it references `SysImage` itself — no `reference-schema-name`.
- `Date` and `Time` are write-time aliases of `DateTime` (also in `sync-schemas` `columns` / `update-operations`); expect `DateTime` from `get-entity-schema-properties`. For a date-only field set `pickerType: "date"` on its `crt.DateTimePicker`.
- Changing a schema's display column, relabeling an inherited column, or adding a `Color` column: read `app-modeling-details` first.

Git-first workspace: capture DB-first schemas before pushing
- This rule owns the create -> capture -> review -> push ordering for a workspace deployed with `push-workspace`.
- After any DB-first schema creation (e.g. `create-entity-schema`, `create-lookup`, `sync-schemas`), MUST capture the affected package with the `restore-workspace` tool (CLI alias `pull-workspace`) before the next push; creation in Creatio does not put the schema in Git.
- Preserve uncommitted local work before pulling; confirm source environment, package selection and destination workspace; review the diff and verify the new schema's identity, metadata and resources are in the package to be published. Only then `push-workspace` to the intended target — a push from an older snapshot can remove DB-only schemas absent from it, so never use a push to capture server-side changes.
- When the workspace `AGENTS.md` prohibits `push-workspace` (an FSM workspace), keep using its prescribed filesystem workflow instead. `export-schema` and tool-contract assumptions: `app-modeling-details`.

Page editing guardrails
- `list-pages` identifies page candidates by `schema-name`.
- Existing-app page/detail backed by data: resolve the backing schema from refreshed context (`get-app-info`, `list-pages`, `get-page`; if still unclear, `get-entity-schema-properties`) before planning schema creation. Call `get-entity-schema-properties` WITHOUT `package-name` (merged schema); an empty single-package read is NOT proof a column is missing — re-read without it or use `find-entity-schema` first.
- If context already exposes a backing supporting or link schema, it is page-only reuse work; do not create a schema because the page does not yet show the detail (worked example: `existing-app-maintenance-details`).
- `get-page` `raw.body` is the editable source of truth: send the full `raw.body` string to `sync-pages` or `update-page`, never `bundle` / `bundle.viewConfig` fragments.
- `sync-pages` for multi-page or plan-driven writes; `update-page` only for a single-page save or dry-run.
- Pass `resources` as a JSON object string when bodies introduce `#ResourceString(key)#` macros.
- For new apps or extended main entities, edit pages after `sync-schemas` and a `get-app-info` refresh, so bindings reference materialized columns.
- Fetch a Freedom UI component's or composite's structure (and assembly recipe) from `get-component-info` instead of hand-assembling or inventing it; `page-modification` owns editing mechanics, `get-guidance` any dedicated authoring article.
